# SQLite Prediction Audit Database Architecture

**Platform**: PayGuard AI Financial Fraud Intelligence Platform  
**Database**: SQLite 3 (`payguard.db`)  
**Module**: `backend/database.py`

---

## 1. Purpose
The SQLite Prediction Audit Database provides lightweight, embedded, persistent audit tracking and history logging for all prediction events generated by the PayGuard AI inference engine. It enables financial compliance auditing, prediction history retrieval, dynamic risk analytics, and detailed prediction inspection.

---

## 2. Architecture Overview
The database layer is decoupled from ML inference logic and implemented in a dedicated module (`backend/database.py`). It uses Python's standard library `sqlite3` driver with thread-safe connection pooling and Write-Ahead Logging (WAL) enabled for concurrency.

```
Incoming Request (HTTP)
         ↓
  ML Model Inference (XGBoost 2.1.4)
         ↓
  Prediction Output Generated
         ↓
  Post-Inference Audit Logger (backend/database.py)
         ↓
  payguard.db (SQLite Table: prediction_audits)
```

---

## 3. SQLite Database Design
- **Database File**: `payguard.db` (located at workspace root).
- **Initialization**: Created automatically during FastAPI application startup/lifespan if missing. Existing databases and records are strictly preserved (`CREATE TABLE IF NOT EXISTS`).

---

## 4. Database Table Schema (`prediction_audits`)

```sql
CREATE TABLE IF NOT EXISTS prediction_audits (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    prediction_id TEXT UNIQUE NOT NULL,
    timestamp TEXT NOT NULL,
    amount REAL NOT NULL,
    transaction_type TEXT NOT NULL,
    fraud_probability REAL NOT NULL,
    is_fraud INTEGER NOT NULL,
    threshold REAL NOT NULL,
    risk_level TEXT NOT NULL,
    model_name TEXT NOT NULL,
    model_version TEXT NOT NULL,
    risk_signals TEXT,  -- JSON string array
    shap_values TEXT,   -- JSON string object
    created_at TEXT NOT NULL
);
```

---

## 5. Indexes
To support high-speed pagination, filtering, and aggregate analytics, the database defines the following secondary indexes:

```sql
CREATE INDEX IF NOT EXISTS idx_is_fraud ON prediction_audits(is_fraud);
CREATE INDEX IF NOT EXISTS idx_risk_level ON prediction_audits(risk_level);
CREATE INDEX IF NOT EXISTS idx_tx_type ON prediction_audits(transaction_type);
CREATE INDEX IF NOT EXISTS idx_created_at ON prediction_audits(created_at);
```
*(Note: `prediction_id` is automatically indexed by SQLite via `TEXT UNIQUE NOT NULL`).*

---

## 6. Prediction Lifecycle
1. **Request Intake**: User submits transaction via API (`POST /api/predict`, `/api/predict/batch`, or `/api/predict/batch/csv`).
2. **Feature Engineering**: Standard ratio feature engineering (`amount_to_oldbalance_ratio`, `type_*`).
3. **XGBoost Inference**: `fraud_xgb_model.pkl` calculates probability score.
4. **Risk & Explanation**: Evaluates against threshold $0.90$, assigns risk level (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`), and computes native Tree SHAP contributions (`pred_contribs=True`).
5. **Post-Inference Logging**: The result payload is passed to `insert_prediction_audit()` or `insert_prediction_audits_bulk()`.
6. **API Response**: Returns the prediction JSON payload immediately to the client.

---

## 7. Single Prediction Logging (`POST /api/predict`)
- Executed **strictly post-inference** after the model successfully completes prediction.
- If database logging encounters an issue, the error is safely caught and logged server-side without failing the user's prediction response.

---

## 8. Batch Prediction Logging (`POST /api/predict/batch` & `csv`)
- Executes bulk insertions using `executemany` with `INSERT OR IGNORE INTO prediction_audits`.
- High-throughput chunk streaming ensures thousands of batch transactions are saved efficiently in milliseconds.

---

## 9. History API (`GET /api/predictions/history`)
- **Parameters**: `limit` (default 20, max 100), `offset` (default 0), `is_fraud` (bool), `risk_level` (str), `transaction_type` (str).
- **SQL Execution**: Executes parameterized `SELECT` queries with `WHERE`, `ORDER BY id DESC`, `LIMIT`, and `OFFSET`.
- **Response**:
  ```json
  {
    "items": [...],
    "total": 100,
    "limit": 20,
    "offset": 0
  }
  ```

---

## 10. Detail API (`GET /api/predictions/{prediction_id}`)
- Fetches the complete stored audit record for a given `prediction_id`.
- Deserializes stored JSON strings (`risk_signals` and `shap_values`) into structured JSON objects.
- Returns **HTTP 404** if the prediction record does not exist in `payguard.db`.

---

## 11. Analytics API (`GET /api/predictions/analytics`)
- Dynamically computes aggregate statistics directly within SQLite using fast SQL aggregations:
  - `COUNT(*)` as `total_predictions`
  - `SUM(is_fraud)` as `fraud_detected`
  - `COUNT(*) - SUM(is_fraud)` as `legitimate_detected`
  - `fraud_detected / total_predictions` as `fraud_rate`
  - `AVG(fraud_probability)` as `average_fraud_probability`
  - `GROUP BY risk_level` for `risk_distribution` (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`).

---

## 12. Duplicate Protection
- Uniqueness is enforced at the database level via `prediction_id TEXT UNIQUE NOT NULL`.
- Insert operations use `INSERT OR IGNORE` to safely drop any redundant attempt to re-insert an existing `prediction_id`.

---

## 13. Error Handling & Safety
- **Post-Inference Guarantee**: Database logging occurs *after* model inference.
- **Fail-Safe Operation**: Database exceptions during logging do not interrupt prediction responses or alter model output.
- **Privacy & Clean Errors**: Stack traces are never exposed over HTTP. Missing prediction records return clean 404 errors.

---

## 14. Privacy Considerations
- Personally identifying transaction account strings (`nameOrig` and `nameDest`) are **not stored** in `prediction_audits`. Only financial parameters (`amount`, `type`, `probability`, `risk_level`, `shap_values`) required for audit compliance are persisted.

---

## 15. Performance Considerations
- Uses SQLite **WAL (Write-Ahead Logging)** mode (`PRAGMA journal_mode=WAL;`) for concurrent read/write locks.
- Queries are strictly indexed and paginated via `LIMIT` and `OFFSET` to prevent high memory usage.
